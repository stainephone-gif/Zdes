# Бэклог MVP: пользовательские истории и критерии приёмки

Оценка в story points (1 SP ≈ 0,5 дня разработчика). Приоритет: **P0** — без этого MVP не существует, **P1** — нужно к релизу, **P2** — можно вынести в первый патч.

Итого по эпикам: **P0 — 95 SP, P1 — 41 SP, P2 — 16 SP.**

Прирост P0 относительно первой редакции — инструменты редактора (US-5.2b,
US-5.2c) и граф городских произведений (US-2.2b, US-5.1b). Первое окупается
тем, что без него база одним человеком не наполняется в срок вообще. Второе —
тем, что закрывает пустой блок «Произведения» у архитекторов и инженеров,
даёт каждой карточке гарантированную связь и удерживает пользователя на улице,
а не отправляет читать книгу вечером.

## Эпик 1. Распознавание (P0, 34 SP)

### US-1.1 — Съёмка таблички (P0, 5 SP)
**Как** прохожий, **я хочу** сфотографировать табличку одним нажатием, **чтобы** не тратить время на настройку.

Критерии приёмки:
- [ ] Приложение открывается на экране камеры, готовность к съёмке ≤ 1,5 с от холодного старта
- [ ] Кнопка съёмки, фонарик, выбор из галереи доступны с первого экрана
- [ ] Фото сжимается до длинной стороны 1600 px, качество 85, размер ≤ 1,5 МБ
- [ ] При отказе в доступе к камере показывается экран-объяснение с кнопкой перехода в настройки
- [ ] При отсутствии геолокации съёмка не блокируется

### US-1.2 — Предпроверка кадра на устройстве (P1, 3 SP)
- [ ] Оценка резкости (дисперсия Лапласиана) ниже порога → подсказка «Держите ровнее» до отправки
- [ ] Слишком тёмный кадр → подсказка «Включите фонарик» с кнопкой включения
- [ ] Подсказка не блокирует съёмку, а предупреждает

### US-1.3 — Серверный пайплайн распознавания (P0, 13 SP)
- [ ] Эндпоинт `POST /v1/recognize` принимает изображение и координаты
- [ ] Препроцессинг: grayscale, CLAHE, выравнивание перспективы, инвертированный проход
- [ ] Гео-фильтр: радиус 75 м, автоматическое расширение до 150 м при < 3 кандидатах
- [ ] OCR-провайдер вынесен за интерфейс — заменяется конфигом без правки логики
- [ ] Извлечение ФИО и годов из распознанного текста
- [ ] Нечёткий матчинг по формуле из §6.1 ТЗ
- [ ] Ответ содержит `status`, `confidence`, до 3 кандидатов
- [ ] p90 времени обработки на сервере ≤ 1,5 с
- [ ] Каждый запрос пишется в `recognition_event`

### US-1.4 — Экран обработки (P0, 3 SP)
- [ ] Три сменяющихся статуса: «Читаю табличку» → «Ищу человека» → «Собираю материалы»
- [ ] Отмена по кнопке «Назад» прерывает запрос
- [ ] При таймауте 15 с — экран неудачи, а не бесконечный индикатор

### US-1.5 — Выбор из кандидатов (P0, 5 SP)
- [ ] При `status: ambiguous` показывается до 3 карточек с фото, именем и адресом
- [ ] Выбор пользователя логируется событием `candidate_chosen` с позицией
- [ ] Есть выход «Ничего из этого» → экран неудачи

### US-1.6 — Экран неудачи с тремя выходами (P0, 5 SP)
- [ ] Текст объясняет причину («не удалось прочитать» / «мы пока не знаем табличек в этом районе») — разные тексты для разных причин
- [ ] Кнопка «Снять ещё раз» с конкретной подсказкой
- [ ] Кнопка «Таблички рядом» → экран «Рядом»
- [ ] Кнопка «Ввести имя вручную» → поиск

## Эпик 2. Карточки и контент (P0, 34 SP)

### US-2.1 — Карточка персоны (P0, 8 SP)
- [ ] Блоки: «Кто это», «Чем важен», «Связь с домом», «Читать/Слушать/Смотреть», «Связи», «Источники»
- [ ] Пустые блоки не отрисовываются (кроме «Источники» — он обязателен всегда)
- [ ] Кнопки «Сохранить», «Поделиться», «Здесь ошибка»
- [ ] Карточка кэшируется в Room и открывается офлайн
- [ ] TalkBack корректно читает все блоки по порядку

### US-2.2 — Переход к произведениям (P0, 5 SP)
- [ ] До 5 ссылок, сгруппированных по типу с иконками
- [ ] Открытие в Custom Tabs; при наличии установленного приложения — дип-линк в него
- [ ] Событие `content_link_tap` с типом и провайдером
- [ ] Битые ссылки (`is_alive = false`) не показываются

### US-2.2b — «Что он построил» (P0, 8 SP)
**Как** прохожий, узнавший об архитекторе, **я хочу** увидеть, что он построил рядом, **чтобы** дойти и посмотреть, а не откладывать на вечер.

- [ ] Блок показывается для персон с ролью architect / engineer / sculptor
- [ ] До 6 работ, сортировка по расстоянию от текущего положения пользователя
- [ ] Подпись расстояния у каждой: «Дом Мельникова, 400 м отсюда»
- [ ] Работы дальше 2 км — отдельной группой «в других районах», без расстояния
- [ ] Без геолокации блок показывается без расстояний, порядок — по году постройки
- [ ] Тап открывает карточку места (S5), отдельный экран не делается
- [ ] Событие `work_card_view` с `work_type`, `authorship`, `distance_m`
- [ ] Пустой блок не отрисовывается

### US-2.3 — Связи (P0, 8 SP)
- [ ] До 6 карточек-переходов, каждая с подписью-объяснением, почему связь здесь
- [ ] Типы: другая табличка того же человека, дом, кто ещё в этом доме, современник в квартале, **автор здания, постройка этого человека**
- [ ] Связь «кто построил этот дом» проставляется автоматически при импорте и гарантирует, что блок «Связи» непустой у каждой карточки
- [ ] Событие `relation_tap` с `depth_in_session`
- [ ] Навигация назад возвращает по цепочке карточек, а не на камеру

### US-2.4 — Карточка места (P1, 5 SP)
- [ ] Адрес, год постройки, архитектор, история 2–4 предложения
- [ ] Архитектор кликабелен и ведёт на его карточку персоны
- [ ] Список всех персон, связанных с домом
- [ ] Источники

## Эпик 3. «Рядом» и страховочные сценарии (P0/P1, 21 SP)

### US-3.1 — Список табличек рядом (P0, 8 SP)
- [ ] Радиус 500 м, сортировка по расстоянию, миниатюра + имя + расстояние
- [ ] Эндпоинт `GET /v1/nearby` использует PostGIS-индекс, p90 ≤ 300 мс
- [ ] Пустой результат → сообщение о границах покрытия с картой зоны
- [ ] Кэш квадрата 1×1 км в Room для офлайна

### US-3.2 — Карта (P1, 8 SP)
- [ ] MapLibre + OSM-тайлы, пины табличек, кластеризация при отдалении
- [ ] Тап по пину → превью-карточка → полная карточка
- [ ] Атрибуция OSM на карте

### US-3.3 — Ручной поиск по имени (P0, 5 SP)
- [ ] `GET /v1/search` с нечётким поиском (`pg_trgm`), подсказки от 3 символов
- [ ] Результат — список персон с адресами табличек
- [ ] Событие `manual_search_used`

## Эпик 4. Мои находки и офлайн (P1, 13 SP)

### US-4.1 — История находок (P1, 8 SP)
- [ ] Хронологический список: дата, фото пользователя, имя персоны
- [ ] Полностью работает офлайн
- [ ] Удаление записи свайпом; удаление всей истории в настройках
- [ ] Фото пользователя хранится только на устройстве

### US-4.2 — Очередь при отсутствии сети (P1, 5 SP)
- [ ] Фото при отсутствии сети ставится в очередь через WorkManager
- [ ] При появлении сети распознавание выполняется автоматически
- [ ] Локальное уведомление «Мы прочитали вашу табличку» с переходом в карточку
- [ ] Очередь очищается через 48 часов

## Эпик 5. Данные и админка (P0, 34 SP)

> Редактор один и совмещает эту работу с ведением продукта. Инструмент должен
> довести стоимость записи с ~25 минут до ~3,5 — иначе база не наполнится
> в срок. Поэтому весь эпик идёт **до** начала наполнения, на неделе 2.
> Расчёт: `docs/06-content-plan.md`.

### US-5.1 — Импорт из открытых источников (P0, 8 SP)
- [ ] Скрипт выгрузки OSM через Overpass API по bbox ЦАО
- [ ] Обогащение из Wikidata по `subject:wikidata`
- [ ] Дедупликация по координатам (радиус 15 м) и нормализованному ФИО
- [ ] Все импортированные записи получают статус `draft`
- [ ] Импорт запускается по bbox коридора и логирует, сколько записей нашлось

### US-5.1b — Импорт построек из Wikidata (P0, 5 SP)
**Как** система, **я хочу** знать, что создал каждый человек в городе, **чтобы** показать это как произведение с расстоянием.

- [ ] По `subject:wikidata` персоны выгружаются работы: P84 (архитектор), P631 (инженер), P170 (автор памятника)
- [ ] Берутся только объекты с координатами (P625) — без координат постройка бесполезна
- [ ] Работы дедуплицируются с уже существующими `place` по координатам
- [ ] Здания в коридорах с тегом `wikidata` в OSM получают связь «автор здания» автоматически
- [ ] Отчёт импорта: сколько персон получили хотя бы одну постройку, сколько построек в пешей доступности

### US-5.2 — Админка редактора (P0, 8 SP)
- [ ] Список записей с фильтром по статусу и наличию источника
- [ ] Редактирование персон, мест, табличек, ссылок, связей
- [ ] Публикация записи невозможна без минимум одного источника — валидация на уровне модели
- [ ] Просмотр отчётов об ошибках от пользователей с переходом к записи
- [ ] Чек-лист из шести пунктов прямо в форме — публикация закрыта, пока не отмечены все
- [ ] Кнопка «Отложить» и отдельная очередь отложенных
- [ ] Счётчик: сколько записей опубликовано по каждому коридору

### US-5.2b — Черновик абзаца «чем важен» (P0, 5 SP)
**Как** редактор-одиночка, **я хочу** получать готовый черновик текста, **чтобы** проверять, а не писать с нуля — это самая долгая часть работы над записью.

- [ ] На вход модели подаётся **текст статьи Википедии**, полученный по ссылке из записи; знания модели о человеке использовать запрещено — это записано в промпте
- [ ] Источник прикрепляется к записи автоматически и не отвязывается при правке
- [ ] Черновик визуально помечен как непроверенный
- [ ] Опубликовать запись, не открыв черновик, невозможно
- [ ] Если статьи-источника нет, черновик не генерируется, поле остаётся пустым

### US-5.2c — Добавление таблички с телефона (P0, 3 SP)
**Как** редактор, **я хочу** добавить табличку прямо на улице, **чтобы** не терять находку, которой нет в OSM.

- [ ] Админка пригодна для работы с телефона
- [ ] Форма: фото, текст надписи, координата подставляется автоматически
- [ ] Запись создаётся со статусом `draft` и попадает в общую очередь верификации

### US-5.3 — Автопроверка ссылок и автогенерация (P1, 5 SP)
- [ ] Поисковые URL в Литрес, Яндекс Музыку и Кинопоиск строятся из ФИО детерминированно при импорте
- [ ] Еженедельная задача проверяет HTTP-статус всех `content_link`
- [ ] Неживые ссылки помечаются `is_alive = false` и попадают в отчёт редактору

## Эпик 6. Аналитика, качество, релиз (P1, 16 SP)

### US-6.1 — События аналитики (P1, 5 SP)
- [ ] Все события из §10 ТЗ реализованы и проверены на дашборде
- [ ] `depth_in_session` считается корректно при навигации по связям
- [ ] Отладочный режим для проверки событий без загрязнения продовых данных

### US-6.2 — Отчёт об ошибке (P1, 3 SP)
- [ ] Форма в один шаг: тип проблемы + комментарий
- [ ] Чекбокс «приложить фото и место» выключен по умолчанию
- [ ] Подтверждение отправки

### US-6.3 — Онбординг и разрешения (P1, 5 SP)
- [ ] Три экрана, показываются один раз, пропускаются кнопкой
- [ ] Карта зоны покрытия на втором экране
- [ ] Объяснение перед системным запросом каждого разрешения

### US-6.4 — Подготовка к публикации (P1, 3 SP)
- [ ] Политика конфиденциальности опубликована по постоянному URL
- [ ] Data Safety в Play Console заполнена
- [ ] Скриншоты, описание, иконка
- [ ] Crashlytics подключён и проверен на тестовом краше
