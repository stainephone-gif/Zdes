# Сколько мемориальных табличек есть в OpenStreetMap

Первое, что надо выяснить перед выбором коридоров: где автозаполнение вообще
сработает. Коридор без данных в OSM собирается только в поле и при одном
редакторе не окупается.

Запрос выполняется на https://overpass-turbo.eu — вставить, нажать «Выполнить».

## Результаты

### Общий подсчёт по центру — выполнено 22.08.2026

bbox `(55.720, 37.540, 55.800, 37.690)`:

```
nodes: 1220   ways: 2   relations: 0   total: 1222
```

**Вывод: данные не являются ограничением.** 1222 объекта против целевых 140
записей — запас почти в девять раз. Узкое место проекта — не наличие
табличек в открытых данных, а пропускная способность одного редактора.

Практические следствия:
1. Коридоры выбираются по **плотности**, а не по принципу «где хоть что-то есть».
2. После релиза есть куда расти годами: очередь неудачных распознаваний
   (`docs/03-test-plan.md` §3.3) будет упираться в редактора, а не в данные.
3. Открывается вариант показывать непроверенные таблички в ограниченном виде —
   см. «Три уровня автоматизации» ниже.

**Чего эта цифра ещё не говорит.** 1222 — это верхняя граница сырых
кандидатов. Часть из них — таблички о событиях, а не о персоналиях, и часть
без полезных тегов. Стоимость записи для редактора определяют два следующих
числа, а не это.

### Разбивка по тегам — выполнено 22.08.2026

| Фильтр | Записей | Доля |
|---|---|---|
| Всего | 1222 | 100% |
| С `inscription` (текст надписи) | 612 | 50,1% |
| С `subject:wikidata` (привязка к персоне) | 120 | 9,8% |
| Оба тега сразу | 52 | 4,3% |

Отсюда четыре непересекающиеся группы:

| Группа | Записей | Доля | Что это значит для редактора |
|---|---|---|---|
| Оба тега | **52** | 4% | Полностью описанная запись: и персона, и текст |
| Только `subject:wikidata` | **68** | 6% | Персона известна — карточка заполняется целиком; нет только буквального текста надписи |
| Только `inscription` | **560** | 46% | Основной пул. Текст есть, персону надо сопоставить |
| Ни того, ни другого | **542** | 44% | Голая координата. В MVP не берём |

**Пригодный пул — 680 записей, 56% от всех.**

**Правило отбора для MVP: 542 записи без обоих тегов не импортируем.** Каждая
стоит редактору 20–25 минут: при бюджете в 12 часов это 30 записей вместо 140.
Они никуда не денутся и разбираются после релиза по очереди неудачных
распознаваний — там хотя бы понятно, какие из них людям реально нужны.

**`subject:wikidata` слишком редок, чтобы на него опираться.** 120 записей на
весь центр — примерно 1,4 на квадратный километр, то есть 2–5 в коридоре.
Маршрут на них не построить. Основная масса базы придёт из пула «только
надпись» (560 записей), и стоимость именно этой группы определяет всё.

**Что говорит доля 4%.** Только 52 таблички из 1222 описаны полностью — и
персона, и текст. Для 90% табличек центра открытые данные не отвечают на
вопрос «кто это»: координата есть, человека нет. Это и есть содержание
продукта — мы не переупаковываем существующие данные, а создаём связь между
табличкой и персоной, которой сейчас нет нигде. Google Lens здесь не помогает
по той же причине.

**Отсюда — самая ценная доработка в проекте:** автосопоставление персоны по
тексту надписи (US-5.1d). Надпись содержит ФИО и годы; разбор и нечёткое
сопоставление у нас уже написаны и проверены (`spike/ocr_bench/matcher.py`),
добавить нужно только поиск по Wikidata. Это переводит группу из 560 записей
с 8–10 минут на 4–6.

### Бонус: бесплатный эталон для проверки OCR

612 надписей с координатами — это готовый размеченный набор. Фотографируя
табличку на шаге 3, эталонный текст выписывать не нужно: он уже есть в OSM.
Достаточно записать идентификатор объекта. Посимвольная точность движка
считается автоматически, без ручной разметки.

### Что ещё стоит уточнить

Пересечение двух множеств — сколько записей имеют оба тега сразу:

```
[out:json][timeout:90];
(
  nwr["memorial"="plaque"]["inscription"]["subject:wikidata"](55.720,37.540,55.800,37.690);
  nwr["memorial:type"="plaque"]["inscription"]["subject:wikidata"](55.720,37.540,55.800,37.690);
  nwr["historic"="memorial"]["inscription"]["subject:wikidata"](55.720,37.540,55.800,37.690);
);
out count;
```

Если пересечение близко к 120 — значит привязанные к персоне записи почти все
несут и надпись, и три группы разделены чисто. Если сильно меньше — есть
записи с wikidata, но без надписи; они всё равно дешёвые, просто нечего
показать как исходный текст.

### Три уровня автоматизации

Пересчёт с учётом полученных чисел:

| Группа | Записей | Что делает редактор | Минут |
|---|---|---|---|
| Оба тега | 52 | подтверждает готовую карточку | 2–4 |
| Только wikidata | 68 | то же; текст надписи при желании вписывает с фото | 3–5 |
| Только надпись, **с автосопоставлением** | 560 | подтверждает предложенную персону | 4–6 |
| Только надпись, без автосопоставления | 560 | ищет персону вручную | 8–10 |
| Ни того ни другого | 542 | **в MVP не берём** | 20–25 |

Стоимость 140 записей при реалистичном наборе (~25 из дешёвого пула,
сколько их попадёт в коридоры, плюс ~115 из пула с надписью):

- **с автосопоставлением: ≈ 11 часов**
- **без него: ≈ 18,5 часа**

Разница — семь с половиной часов работы одного человека, и это единственная
задача бэклога с такой отдачей.

#### Сколько записей с текстом надписи

```
[out:json][timeout:90];
(
  nwr["memorial"="plaque"]["inscription"](55.720,37.540,55.800,37.690);
  nwr["memorial:type"="plaque"]["inscription"](55.720,37.540,55.800,37.690);
  nwr["historic"="memorial"]["inscription"](55.720,37.540,55.800,37.690);
);
out count;
```

Текст надписи ценен вдвойне: он и в базу идёт, и служит эталоном для проверки
OCR — по нему считается посимвольная точность движка без ручной разметки.

#### Сколько записей с привязкой к персоне

```
[out:json][timeout:90];
(
  nwr["memorial"="plaque"]["subject:wikidata"](55.720,37.540,55.800,37.690);
  nwr["memorial:type"="plaque"]["subject:wikidata"](55.720,37.540,55.800,37.690);
  nwr["historic"="memorial"]["subject:wikidata"](55.720,37.540,55.800,37.690);
);
out count;
```

**Это главное число проекта.** Оно определяет и стоимость записи, и то,
сколько персон получат годы жизни, род занятий и постройки без участия
человека.

## Выгрузка с тегами — то, что пойдёт в импорт

```
[out:json][timeout:90];
(
  nwr["memorial"="plaque"](55.720,37.540,55.800,37.690);
  nwr["memorial:type"="plaque"](55.720,37.540,55.800,37.690);
  nwr["historic"="memorial"]["inscription"](55.720,37.540,55.800,37.690);
);
out center tags;
```

Полезные теги в ответе:

| Тег | Что даёт |
|---|---|
| `inscription` | текст надписи — сразу и в базу, и как эталон для проверки OCR |
| `subject:wikidata` | идентификатор персоны: отсюда тянутся годы, род занятий, связи |
| `name` | подпись объекта |
| `addr:street`, `addr:housenumber` | адрес дома |
| `start_date` | год установки |

## Как читать результат по коридорам

При общей плотности 1222 объекта на центр пороги сдвигаются вверх — выбираем
не «где есть данные», а «где их больше всего»:

- **Больше 80 в коридоре** — брать не думая.
- **40–80** — рабочий вариант.
- **Меньше 40** — есть варианты лучше, смотреть соседние кварталы.

Считать по каждому коридору **два числа**: общее и с `inscription`. Именно
надпись, а не `subject:wikidata` — последний слишком редок (120 на весь
центр), чтобы различать по нему коридоры.

Коридор с 60 записями, из которых 45 с надписью, лучше коридора со 100
записями, где надписей 20: во втором случае 80 объектов — это голые
координаты, которые мы всё равно не берём.

Записать числа сюда и зафиксировать выбор трёх коридоров в
`docs/06-content-plan.md` §2.

## Персоналии из Wikidata

По `subject:wikidata` из выгрузки — запрос на https://query.wikidata.org:

```sparql
SELECT ?person ?personLabel ?birth ?death ?occupationLabel ?article WHERE {
  VALUES ?person { wd:Q1234 wd:Q5678 }   # идентификаторы из тега subject:wikidata
  OPTIONAL { ?person wdt:P569 ?birth. }
  OPTIONAL { ?person wdt:P570 ?death. }
  OPTIONAL { ?person wdt:P106 ?occupation. }
  OPTIONAL {
    ?article schema:about ?person;
             schema:isPartOf <https://ru.wikipedia.org/>.
  }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "ru". }
}
```

Отсюда берутся годы жизни, род занятий и ссылка на статью — то есть три из
шести полей карточки заполняются без участия редактора.

## Постройки: что эти люди создали в городе

Для архитекторов, инженеров и скульпторов произведение — это не ссылка,
а объект в городе с координатами. Проверяем, сколько таких объектов есть
в Wikidata по нашим персонам.

```sparql
SELECT ?person ?personLabel ?work ?workLabel ?role ?coord ?built ?typeLabel WHERE {
  VALUES ?person { wd:Q1234 wd:Q5678 }   # идентификаторы из subject:wikidata

  {  ?work wdt:P84  ?person. BIND("architect" AS ?role) }   # архитектор здания
  UNION
  {  ?work wdt:P631 ?person. BIND("engineer"  AS ?role) }   # инженер-конструктор
  UNION
  {  ?work wdt:P170 ?person. BIND("sculptor"  AS ?role) }   # автор памятника

  ?work wdt:P625 ?coord.                 # без координат постройка нам не нужна
  OPTIONAL { ?work wdt:P571 ?built. }
  OPTIONAL { ?work wdt:P31 ?type. }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "ru". }
}
```

Что смотреть в результате:

- **Сколько персон из наших коридоров получили хотя бы одну постройку.** Если
  меньше четверти — блок «Что он построил» переносится в P2, он не окупит
  разработку.
- **Сколько построек попадает в пешую доступность** (до 2 км от таблички).
  Это и есть ценность функции: постройка за сорок километров — это ссылка,
  постройка за четыреста метров — это повод пройтись.

## Автор дома, на котором висит табличка

Здания в OSM часто несут тег `wikidata`. Через него у дома находится
архитектор, и это даёт связь для **любой** таблички, даже если у самой
персоны нет ни одного произведения.

```
[out:json][timeout:90];
way["building"]["wikidata"](55.720,37.540,55.800,37.690);
out center tags;
```

Дальше по полученным идентификаторам — свойство P84 в Wikidata. Посчитать,
у какой доли зданий в коридорах есть такой тег: это верхняя граница
автоматического заполнения связи «кто построил этот дом».
